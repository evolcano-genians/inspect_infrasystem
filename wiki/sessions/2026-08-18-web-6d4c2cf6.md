## 결론

- **조사 대상**
  - AWS dev Kubernetes의 `nexus-lake` Silver 계층과 소비 앱 `security-view`.
  - Tenant 스키마: `delta.tenant_genians`.
  - 확인된 Silver 7개: `tatum_assets`, `tatum_entities`, `tatum_remediations`, `ztna_devices`, `edr_endpoints`, `edr114_90_xba`, `ztna99_65_admin_activities`.
  - 관련 워크로드: `trino`, `hive-metastore`, `bronze-ingestor`, `registry-api`, `security-view-backend`.

- **파이프라인·스키마 구조**
  - Silver는 고정 스키마가 아니라 Postgres tenant registry의 resource 정의로 동적 생성됨.
  - Bronze 원본 JSON을 파서 계약에 따라 평탄화하고 Delta Silver 테이블을 promotion 주기마다 `overwrite`.
  - Tenant는 `tenant_id` 컬럼이 아니라 `tenant_genians` 같은 스키마로 분리.
  - 공통 메타컬럼 7개: `kafka_topic`, `kafka_partition`, `kafka_offset`, `kafka_timestamp`, `ingested_at`, `resource_id`, `message_key`.
  - `raw_value`는 promotion schema에 명시되지 않으면 Silver에서 제거됨.

- **2026-08-05 실측 인벤토리**
  - `tatum_assets`: 3,329행, `id` 중복 없음. 주요 필드 `id`, `assetname`, `provider`, `assettype`, `region`, `ipaddr`, `assetmanager`; 자산 검색·provider/type/region 집계에 사용.
  - `tatum_entities`: 116행, `id` 중복 없음. 주요 필드 `id`, `entityname`, `entitytype`, `accountid`, `writepermissionexist`, `consoleuser`, `mfaenabled`, `activestatus`, `accesskeyids`, `createdTime`, `lastActivity`; IAM·권한·MFA 분석에 사용.
  - `tatum_entities.mfaenabled`: 116행 중 `'N/A'` 98행. MFA 비율은 전체가 아니라 `consoleuser=true`인 18행을 분모로 사용해야 함.
  - `tatum_remediations`: 91행, `tatumpolicyid` 중복 없음. 주요 필드 `tatumpolicyid`, `policyname`, `provider`, `severity`, `failcount`, `passcount`, `nacount`; CSPM 위반·조치 대상 분석에 사용.
  - `tatum_remediations`: `failcount` 합계 697, `passcount`·`nacount` 합계 0. 카운트가 문자열일 수 있어 `try_cast` 필요하며 준수율 계산에 부적합.

  - `edr114_90_xba`: 1행, EDR 탐지 이벤트; `detecttime`은 epoch-ms 문자열.

- **확인된 소비·매핑**
  - `security-view`가 논리 이름 `cloud_assets`, `cloud_entities`, `cloud_policies`, `cloud_scan_reports`, `edr_endpoints`, `edr_threats`, `nac_nodes`를 환경변수로 사용.
  - 실제 Delta 이름은 `tatum_assets`, `tatum_entities`, `tatum_remediations`, `ztna_devices`, `edr114_90_xba` 등으로 달라 명시적 매핑이 필요.
  - 주요 용도는 클라우드/Kubernetes 자산, IAM·MFA, CSPM 정책 위반, NAC 장비, EDR 엔드포인트·탐지, 관리자 활동 조회.

- **리소스 문제·결론**
  - 높은 위험: 앱이 참조한 `tatum_scan_reports` 실테이블이 2026-08-05 존재하지 않았고 현재도 `SECURITY_TABLE_CLOUD_SCAN_REPORTS` 설정이 남아 있어 빈 결과·쿼리 오류 가능.
  - 높은 위험: 당시 `SECURITY_SCHEMA=tenant_genians`가 로그인 tenant와 무관하게 고정되어 멀티테넌트 오조회·데이터 경계 위반 가능.
  - 중간 위험: `ztna_devices` 중복으로 단순 자산 수가 과대 계산될 수 있음.
  - 중간 위험: 논리명과 실제 테이블명 불일치로 매핑 누락 시 조회 장애 가능.
  - 중간 위험: Bronze 대용량 직접 조회는 Trino OOM·지연 가능; topic/time 필터와 `LIMIT` 필요.
  - 중간 위험: append topic 누적 상태에서 Silver 전체 `overwrite`는 승격 시간과 S3 I/O가 계속 증가하는 구조.
  - 낮은 위험: `security-view-backend`는 당시 Helm 외부 배포여서 재배포·클러스터 재구축 시 유실 가능.
  - 낮은 위험: `bronze-ingestor` 재시작 1회가 있으나 현재 Ready이고 적재 지속, 즉시 장애 증거는 없음.
  - 현재 Kubernetes 기준 관련 워크로드는 모두 Ready이며 즉시 장애 이벤트는 관찰되지 않음.

  - 현재도 tenant 스키마가 하드코딩됐는지, `security-view` 논리명→물리명 매핑이 정상인지 재검증 필요.
