# 세션 web-d599a212 (2026-08-18)

## 질문

aws dev k8s 스토리지와 차이점 알려줘

## 결론

**결론:** Nexus Lake의 대용량 데이터 저장 방식은 **AWS dev는 S3(`s3a://`)**, **Azure dev는 Azure Blob Storage의 ADLS Gen2 인터페이스(`abfs[s]://`/DFS endpoint)**라는 차이가 핵심입니다. 애플리케이션 구조는 둘 다 Spark·Hive Metastore·Trino·Delta Lake로 거의 같습니다.

| 구분 | AWS dev | Azure dev |
|---|---|---|
| 오브젝트 스토리지 | AWS S3 | Azure Blob Storage / ADLS Gen2 |
| Hadoop 접근 방식 | S3A connector, `s3a://bucket/...` | ABFS connector, `*.dfs.core.windows.net` |
| 관찰된 저장소 | 차트상 `provider: aws` 지원 | 계정 `genianobjstore`, 컨테이너 `cloudbackup` |
| 데이터 경로 | `s3a://<bucket>/tenants/...` | `cloudbackup/tenants/<tenant>/datalake/...` |
| 인증 방식 | AWS access key/session token 또는 역할 기반 구성 | Azure 계정 키·SAS·서비스 주체 계열 구성 |
| 데이터용 PVC | S3 자체는 PVC 불필요 | Azure Blob 자체도 PVC 불필요 |
| 현재 특이사항 | AWS 런타임은 이번 세션에서 직접 확인하지 못함 | Blob 기능 충돌로 Bronze 적재 HTTP 409 발생 |

**Kubernetes 내부 저장소**
- Azure에서 Kafka 40Gi, PostgreSQL 20Gi, Kestra 20Gi 등은 `block` StorageClass를 사용합니다.
- 공유 앱 데이터와 Hive JAR는 `shared` StorageClass를 사용합니다.
- `data-minio-0` 20Gi PVC는 남아 있지만 MinIO 워크로드·서비스는 없어 현재 lakehouse 데이터 저장소가 아닙니다.
- AWS의 Kafka/PostgreSQL 등 PVC StorageClass와 용량은 현재 도구가 Azure 컨텍스트에 연결돼 있어 직접 비교할 수 없습니다. 즉, AWS의 **오브젝트 저장 방식은 S3로 비교 가능하지만 PVC 구현 차이는 미확인**입니다.

Helm 차트도 `minio`와 `aws` provider를 S3A 방식으로 처리하며, 기본 경로를 `s3a://<bucket>`으로 생성합니다(`backend-nexus-shell/templates/lakehouse-runtime-configmap.yaml:1`). 반면 현재 Azure의 ABFS 구성은 배포 시 별도 환경 오버라이드로 주입된 것으로 보입니다. 관찰 기준은 **2026-08-18**입니다.
